# アプリのアイデアの扱い方

調べれば欠点は必ず見つかる。机の上で勝てるかを判断しようとすると、やらない理由がたまって手が止まる。
勝てるかではなく「安く試せるか」で選び、出してから市場の反応で続けるかを決める。

引数がなければ、ユーザーの発言から下の3つのどれに当たるかを判断する。迷ったら確認する。

## 1. ためる（探すのと決めるのを分ける）

アイデアが出たら、その場で評価しない。

- 当日の daily（`~/Documents/notes/010_Daily/YYYY-MM-DD.md`）の `# △ log` に `#ネタ` で1行書く。書式は daily-log ルールに従う
- 競合調査や市場の評価はしない。「ニッチ」「競合がいる」などのコメントも付けない
- 「探さなきゃ」と促さない。普段の生活で「面倒だな」と思ったことを書きためれば十分と伝える

## 2. 決める（安く試せるかで選ぶ）

### 候補を集める

```bash
grep -rh "#ネタ" ~/Documents/notes/010_Daily/ | sort | uniq
```

アプリになりそうなものを拾い、ユーザーと一緒に候補を数個に絞る。

### 試す条件で振り分ける

3つすべてを満たすかを見る。満たさないものは「今は試さない」に置き、捨てない。

| 条件 | 中身 |
|------|------|
| 3週間で公開できる | 審査を含めて3週間。根拠は nopace の実績（初コミットから公開まで21日）。収まらなければ機能を削る |
| サーバーなしで動く | データは端末か iCloud（CloudKit）。課金は StoreKit 2（Apple ID）で、アカウントの仕組みは作らない。外部の AI が要るなら有料の追加機能に分け、中継は Cloudflare Workers 1つまで。中継を止めても中心の機能が動く |
| 閉じるのが楽 | 個人情報を持たない。止めても利用者のデータが iCloud に残る |

### 調べるのは2点だけ

app-ranking MCP で調べるのは次の2点に限る。欠点探しを目的にしない。

1. **すでに埋まっていないか**: 公式アプリや無料のオープンソースが同じことを完全にこなしていれば見送る
2. **需要の痕跡があるか**: 似た用途のアプリがランキングに入っているか、評価が低くても上位にいるアプリがあるか

市場が小さいことや、有料の競合がいることは見送る理由にしない。3週間で試せるなら出してみる。
App Store の審査ガイドラインに触れそうなもの（動画の保存、名前に関係ない検索語を詰める、など）は見送る。

### 1本に決めて記録する

- 候補が複数残ったら、一番安く試せるものを1本選ぶ。「一番良い案」を探さない
- 3週間に収まる機能の範囲をユーザーと決める
- やめる基準を決める（下の3を参照）
- `~/Documents/notes/020_Ideas/アプリの試し打ち.md` の表に1行追加する。ファイルがなければ作る

```markdown
| アプリ | 公開予定日 | 判定日 | やめる基準 | 結果 |
|--------|-----------|--------|-----------|------|
| （アプリ名） | YYYY-MM-DD | 公開予定日の3か月後 | 3か月でカテゴリ100位以内に一度も入らない | |
```

## 3. やめる（基準を先に決めておく）

### 既定値

**公開から3か月で、狙ったカテゴリの100位以内に一度も入らなければ、更新をやめて次へ進む。**

- カテゴリで入りやすさが大きく違うので、総合順位ではなくカテゴリ内の順位で見る
- ユーザーが変えたいときだけ、出す前に変える。変えないなら既定値を使う。毎回ゼロから考えさせない

### 判定日に確かめる

1. `アプリの試し打ち.md` から判定日が来たアプリを探す
2. app-ranking MCP の `get_app_history`（`days` を公開日からの日数に合わせる）で、カテゴリ内の最高順位を確かめる
3. 基準を満たさなければ「更新をやめる」と伝え、表の「結果」を埋める。続けるかどうかで迷わせない
4. 次の候補を「2. 決める」から選ぶ

app-ranking のデータはカテゴリの上位200位までで、取得は月1回程度のこともある。圏外ならデータがないので「100位以内に入っていない」と扱う。

## 守ること

- 調べた結果がやらない理由ばかりになったら、そこで調べるのをやめ、試す条件を満たすかだけで判断する
- 見送った案は消さない。条件が変われば試す候補に戻る
