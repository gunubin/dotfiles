# 種類別の型

どの型も、タイトル直下の結論（2〜3文）から始める。
各型の「外せないもの」を省くと、その型にした意味がなくなる。

[dogum/html-artifacts](https://github.com/dogum/html-artifacts) の `references/exploration-and-planning.md`、`reports-and-research.md`、`code-review-and-pr.md`、`diagrams-and-illustrations.md` を日本語に訳して要約し、調査結果の型を足した。

## 比較

2つ以上の選択肢から1つを選ぶとき。

**構成**
- 選択肢ごとに1列（4つ以上ならカードを折り返して並べる）
- 各列は同じ順番・同じ小見出しにする。横に目を動かすだけで比べられるように
- 各列の中身: 一言の要約、実物（コード・画面・設定の抜粋）、長所と短所、数値の指標
- 最後に推奨: どれを選ぶかと理由

**外せないもの**
- 長所と短所は箇条書きではなく表にする。箇条書きは順に読まれ、表は比べて読まれる
- 数値の指標（サイズ、手間、影響範囲など）。数値があると推奨の根拠を示せる
- 全列で同じ項目を埋める。1列だけ項目がないと、その選択肢が劣っていると読まれる

**よくある失敗**
- コードを冒頭にまとめ、比較を下に置く。実物は比較の一部として各列に入れる
- 推奨を書かない
- 8割同じ中身の選択肢を別々に並べる。それは1つの選択肢の設定違い

## 実装計画

作るものは決まっていて、進め方をまとめるとき。

**構成**
- 解く問題を1段落
- マイルストーンを時系列の帯で描く（番号付きリストにしない）
- データの流れの図（インライン SVG）
- 壊れやすい箇所のコード2〜3個と、要注意の行への注記
- リスクの表（リスク / 起きやすさ / 対策）
- やらないことの一覧

**外せないもの**
- データの流れの図。部品が3つ以上あると、文章だけでは構造を頭に保てない
- リスクの表。段落で書いたリスクは流され、表にしたリスクは対処される
- やらないこと。範囲が広がるのを先に防ぐ

**よくある失敗**
- 触るファイルを全部並べる。読み手に要るのは変更の形で、一覧ではない

## 調査結果

原因の調査、ネットや手元で調べた結果をまとめるとき。

**構成**
- 結論: わかったことと、次にやるべきこと
- 見出しは主張にする（「原因は〇〇だった」「〇〇は使えない」）
- 根拠: 確かめたファイル・URL・コマンドの結果を、主張のすぐ下に置く
- まだわかっていないこと: 確かめられなかったことを分けて書く
- 出典の一覧

**外せないもの**
- 確かめたことと推測を分けること。推測には「未確認」と書く
- 根拠を主張の近くに置くこと。末尾にまとめると、どの主張の根拠か追えない

**よくある失敗**
- 調べた順に書く。読み手が知りたいのは調べた過程ではなく結論

## 概念の解説

技術や仕組みを理解したいとき（「〇〇ってどう動くの？」）。

**構成**
- 要点: これから何がわかるかを15秒で伝える。答えを先に言う
- 核心を1文で書き、一番大事な語を強調する
- 素朴なやり方との比較表。「よい」ではなく数値や具体的な違いで比べる
- 実際に使われている場所（読み手が知っているシステムや道具）
- 用語の説明は、本文の横か初出の位置に置く（末尾の用語集は読まれない）
- 状態や位置で理解する仕組み（キュー、ハッシュ、スケジューリングなど）は、スライダーやボタンで動かせるデモを付ける

**よくある失敗**
- 百科事典のような概要から始める。読み手には問いがあるので、まず答える
- 「読み手が想像できる」としてデモや図を省く

## コードの解説

コードベースの機能やモジュールを理解したいとき（「この認証の流れは？」）。

**構成**
- 冒頭の要約: 何をするか、どこにあるか、主なファイル
- モジュールのつながりの図。いちばんよく通る経路を別の色で強調する
- 入口を目的別に書く（「〇〇したいなら △△ から読む」）
- 処理の段階ごとの折りたたみ。概要は開き、深い部分は閉じておく
- 重要な行に注記を付けたコード（注記なしのコードブロックを並べない）
- 実際の入力を1つ選び、どう流れるかを追う

**外せないもの**
- 図。全体の形を一目で見せる
- よく通る経路の強調。まず普通の場合を理解させ、例外は後にする

**よくある失敗**
- ファイル同士の関係をすべて線で結ぶ。構造上の関係だけ描く
- API ドキュメントのように網羅する。これは解説で、リファレンスではない

## 図解

処理の流れ、システムの構成を見せるとき。

**構成**
- インライン SVG で描く。ASCII 図や「〇〇のような流れを想像して」で済ませない
- 正常な経路を強調し、失敗やリトライの経路は控えめな色にする
- 矢印で向きを示す
- 凡例
- ノードの詳細は、クリックで開く横の欄か、図の下の説明に分ける

**外せないもの**
- 図の上に全部を書き込まない。図は案内図で、詳しい中身は別の欄に置く
- 色だけで区別しない。形や線の種類も変える

**描き方**
- 座標は `viewBox` で指定し、幅と高さを固定しない
- 線と文字の色は `currentColor` かテーマの色にする。ダークモードでも見えるように
- 自動配置で線が絡まったら、ノードを手で配置する
- ノードが多すぎるときは、まれな分岐を「エラー処理」などの1つにまとめる
