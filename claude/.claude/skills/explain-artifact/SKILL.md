# explain-artifact

人間が読んで理解・判断するための長い出力を、ターミナルの Markdown ではなく Artifact のページにする。
判断の基準と種類別の型は [dogum/html-artifacts](https://github.com/dogum/html-artifacts)（Apache-2.0）を下敷きにしている（出典は末尾）。

## 1. Artifact にするか決める

次のどれかに当てはまれば Artifact にする。

- **長い説明・調査結果**: 見出しが3つ以上、またはターミナルで1画面を超える
- **比較**: 2つ以上の選択肢を並べて選ぶ。縦に並べるより横に並べた方が比べやすい
- **設計・計画**: 部品のつながりやデータの流れがある。文章だけでは構造を頭に保てない
- **判断の材料**: ユーザーが読んだあとに何かを決める
- **位置や色が意味を持つ**: 差分、時系列、状態、重要度

次のときはターミナルの Markdown のままにする。

- 会話の返答や、数文で答えられる質問
- コード・設定・コマンド・適用する差分そのもの
- 作業の完了報告や確認結果（git pull の確認など）
- 一度読んで捨てる要約（「このファイル何してる？」）
- git で管理し、PR で差分を見るドキュメント
- ユーザーが Markdown やほかの形式を指定したとき

迷ったら「ユーザーはこれを一度読む以上のこと（判断・共有・見返し）をするか」で決める。しないならターミナルにする。
Artifact は Markdown の数倍のトークンと時間がかかるので、使う理由を作り出さない。

## 2. 種類を決めて型を読む

[references/genres.md](references/genres.md) から内容に合う型を読む。2つにまたがるなら両方読む。

| 内容 | 型 |
|---|---|
| 選択肢の比較、どれを選ぶか | 比較 |
| 作るものが決まっていて、進め方をまとめる | 実装計画 |
| 調べた結果、原因の調査 | 調査結果 |
| 概念・技術の仕組み | 概念の解説 |
| コードベースの機能・モジュールの説明 | コードの解説 |
| 処理の流れ、構成 | 図解 |

## 3. ページを作る

1. Artifact ツールのルールに従う（`quickstart` は intent `other`、`artifact-design` スキルのページの決まり）
2. 本文の日本語は `japanese-tech-writing` スキルの規範に従う
3. 全種類に共通する決まり
   - **5秒でわかる**: タイトルの直下に、結論を2〜3文で書く。答えを後ろに隠さない
   - **見出しは主張にする**: 「背景」ではなく「原因は〇〇のキャッシュだった」。見出しだけ読めば筋が追える
   - **Markdown の翻訳にしない**: 比較は列に並べる、流れは図に描く、差分は差分として描く。見出しと段落だけのページなら Markdown でよかった
   - **詳細は折りたたむ**: ログ、長いコード、根拠の生データは `<details>` に入れる
   - **推奨を書く**: 選択肢を並べたら、どれを選ぶか理由つきで書く。「場合による」で終わらせない
   - **根拠を書く**: 調べたファイル、URL、コマンドの結果など、確かめた元をページに残す

## 4. ターミナルに返す

ページの中身はターミナルに繰り返さない。次だけを書く。

```
<結論を2〜4行。Artifact を開かなくても要点がわかるように>

<Artifact の URL>
```

ユーザーに判断を求めるときは、何を決めてほしいかを1行足す。
