## 各セクションの書き方

### 何をしているか

- 差分を読めば分かることの繰り返しは避ける
- 「〜を追加」「〜を変更」の羅列ではなく、変更前後で振る舞いがどう変わったかを書く

### なぜ・どこに効くか

- 差分の外の情報こそ価値がある。周辺コードを読んで得た文脈を書く
- 既存の類似実装があれば示す（一貫性の判断材料になる）

### 🧑 人間が判断すべきこと

AI では確定できず、人間の知識・判断が要る問いを出す。
汎用的なチェックリストではなく、**このチャンク固有の具体的な問い**にする。

良い問いの観点:

| 観点 | 問いの例 |
|------|----------|
| 意図との整合 | 「無効ユーザーも検索結果に含める仕様で合っているか」 |
| ドメイン | 「退会済みユーザーの扱いは業務上どうあるべきか」 |
| 設計判断 | 「新しい抽象クラスを導入しているが、実装が1つしかない現状で必要か」 |
| 前提の妥当性 | 「`items` が常に1件以上という前提を置いているが、保証されているか」 |
| 単純さ | 「既存の `formatDate` で代替できないか」 |
| テストの意味 | 「このテストは実装をなぞっているだけで、仕様を検証していないのでは」 |
| 保守性 | 「半年後にこのフラグの意味を説明できるか」 |

悪い問いの例:

- 「エラーハンドリングは適切ですか？」（汎用的すぎる）
- 「命名は分かりやすいですか？」（具体的な候補がない）

### 🤖 AIが気になった点

- バグ候補、境界値、null/undefined、競合、セキュリティ、パフォーマンス、既存規約（CLAUDE.md / rules）との不整合を検出する
- 確信度が低いものは「可能性」と明記する
- 根拠を `path:line` で示す。推測だけの指摘はしない
- 人間の判断を先に促すため、このセクションは必ず最後に置く
