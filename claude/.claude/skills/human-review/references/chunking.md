# チャンク分割と順序付け

## チャンクの粒度

1チャンクは「1回で頭に収まる論理的なまとまり」とする。
目安は差分 30〜150 行。

| 状況 | 扱い |
|------|------|
| 1ファイルが大きい（150行超） | 関数・クラス・hunk 群など論理単位で分割する |
| 小さな関連ファイルが複数ある | 1チャンクにまとめる（例: 型定義と re-export する index、interface と mock） |
| 同じ機械的変更が多数のファイルにある | 代表1件を見せ、残りは「同種の変更: N files」として1チャンクにまとめる |
| ファイル移動・リネームのみ | 内容差分がなければ「その他」にまとめる |

## 分類と順序

依存の上流から読む。
「何を約束したか」を先に理解すると、実装を読むときの判断が速くなるためである。

| 順 | 分類 | 含むもの |
|----|------|----------|
| 1 | 契約 | 型定義、GraphQL/OpenAPI schema、interface、DB migration、公開 API のシグネチャ、定数・enum |
| 2 | コア | ドメインロジック、service / usecase、アルゴリズム、状態管理 |
| 3 | 配線 | handler、resolver、DI、ルーティング、UI コンポーネント、CLI エントリ |
| 4 | テスト | ユニット・統合・E2E テスト、fixture |
| 5 | その他 | 設定ファイル、生成コード、lock ファイル、ドキュメント、CI |

### 分類内の順序

- 他チャンクから参照される側を先に置く
- 同程度なら、変更の中心（意図に最も直結する部分）を先に置く
- テストは対応する実装チャンクの順に並べる

### 「その他」の扱い

生成コード・lock ファイルは差分全文を表示しない。
「何が変わったか」の要約と、確認すべき点（意図しない依存追加・バージョン変更など）だけを示す。
ユーザーが全文を求めたら表示する。

## 判断に迷う場合

- 分類が曖昧なファイルは、そのファイルを読んで「他から使われる側か、使う側か」で決める
- 循環的に依存する変更は、意図に近い方を先に置き、マップの「この順番の理由」で一言触れる
- 変更が小さい（全体で 100 行未満・3ファイル以下）なら、分類にこだわらず 1〜2 チャンクでよい
