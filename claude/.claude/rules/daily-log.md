# Obsidian Daily ログ

ユーザー本人の体験を、Obsidian の当日の daily ノートに自分から追記する。ユーザーに確認は取らない。

## 記録するのはユーザーの体験だけ

daily はユーザーの日記であり、Claude の作業ログではない。

- 記録する: ユーザーが詰まったこと、ユーザーが知って反応したこと（「なるほど」「知らなかった」）、ユーザーの判断・方針・感想、ユーザーがやったこと
- 記録しない: Claude が調査して得た知識、Claude が実装中に遭遇したエラーやハマりどころ、Claude が書いたコードの内容

根拠はユーザーの発言と行動に限る。「ユーザーが本当にそれを経験したか」で判断し、迷ったら書かない。

## 書き込み先

- ファイル: `~/Documents/notes/015_Logs/YYYY-MM-DD.md`（当日の日付）
- daily ノート（`010_Daily/YYYY-MM-DD.md`）には書かない。daily の `# △ log` から `![[015_Logs/YYYY-MM-DD]]` で埋め込んで表示している
- 追記先: ファイル末尾（見出しは不要。箇条書きだけを並べる）
- ファイルがなければ、先頭に `---\ntype: flow\ntags:\n  - log\n---` を置いて新規作成する
- daily ノート側の埋め込み行はテンプレートに入っているので、触らなくてよい
- Obsidian MCP は Obsidian 起動中しか使えないため、ファイルを直接編集する

## 記録するタイミングと種類

| タグ | いつ書くか | 書く内容 |
|------|-----------|---------|
| `#詰まり` | ユーザーが困っていたことが解決した直後 | ユーザーが何に困り、どう解決したか |
| `#ナレッジ` | ユーザーが新しく知って反応したとき | ユーザーが何を知ったか |
| `#ネタ` | ユーザーの体験・失敗・判断が記事になりそうなとき | 一言の切り口 |
| `#作業` | ひとまとまりのタスクが終わったとき | ユーザーが何をしたか・何を決めたか |

## 粒度

1つのテーマ・判断につき1件にする。日記として読み返したときに「その日に何をして、なぜそう決めたか」がわかればよい。

- 同じテーマが続いたら、新しい項目を足さずに、当日の既存の項目を書き換えて育てる（時刻は最初のまま）。試行錯誤の経過は子項目に1行でまとめる
	- 例: 演出を火花→紙吹雪→波紋→きらめきと試した日は、`#作業` 1件に「最終的に何にしたか」を書き、経過は子項目にする
- 本文は「何をしたか・何を決めたか」を1行で書く。子項目には git に残らないことを書く: 理由、迷い・不安・感想、試してやめたことと、やめた理由
- 実装の細部（設定値、ファイル名、文字や記号の種類など）は書かない。git の履歴に残っている
- `#ネタ` が `#作業` と同じ出来事なら、独立した項目にせず、その `#作業` の子項目に `ネタ:` を付けて書く。独立させるのは、作業と関係なく記事の切り口が浮かんだときだけ
- 追記前に当日分のログファイルを読み、同じテーマの項目があればそれを書き換える

## 書式

1件1項目。時刻とリポジトリ名を先頭に付け、理由や経過は子項目に書く。

```markdown
- 09:42 `mono-and.blog` #詰まり Supabase でカラム追加のたびに migration を書くのが面倒だった
	- 解決: Drizzle を入れて push で済ませるようにした
- 10:30 `mono-and.blog` #作業 Claude Code mods を試して止め、作業中の体験を daily に残す運用に決めた
	- mods で画面に出すより、あとで読み返せる記録の方が欲しかった
	- ネタ: Claude Code mods を試したが、結局 daily への記録の方が欲しかった
```

- 時刻は `date +%H:%M` で取得する
- リポジトリ名はカレントディレクトリのリポジトリ名を使う
- 機密情報（APIキー、顧客名、社内URL）は書かない
- 追記したことはユーザーへの返答の最後に 1 行で伝える（例: 「daily に #詰まり を 1 件記録しました」）
